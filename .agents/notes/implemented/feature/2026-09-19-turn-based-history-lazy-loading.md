# Agent Note: 对话历史采用轮次级分页彻底消除与中间折叠的切片冲突

Status: implemented

## Problem

在 BlackBerry Q20 (720x720 方屏，2GB RAM) 上，历史消息同时存在两种缩减机制：
1. **轮次过程折叠**（Turn Process Fold）：将单轮内的思考过程、工具调用等中间节点聚合折叠为单行，保留 `[用户提问 -> 过程折叠行 -> 最终回答]` 的阅读流。
2. **历史分页懒加载**（Lazy Loading）：防止长会话一次性解压过大 JSON 与膨胀 DOM 导致低内存假死。

但此前历史分页是按**原始消息条数（如每页 20 条）**机械切片的。如果某轮产生大量工具调用（例如一次轮次包含 15 个 step/tool 调用），这一轮就会占满分页切片，导致：
- 用户提问与最终回答被切断在不同的数据页中，形成“断头轮次”；
- 客户端不得不引入复杂的向上自动拉取补齐逻辑（`maybeFillToTurnStart` / `runTurnFill`），逻辑脆弱且与折叠聚合计数冲突；
- 界面上的“加载更多历史消息（X／Y）”文案按原始中间消息计数，而用户在界面上感知的是“对话轮次”，两者口径严重不一致。

## Decision

将历史分页的治理单元从**“原始消息条数”**升级为**“对话轮次（Turn）”**，实现两者有机融合：

1. **服务端 `/api/history` 增强轮次切片**：
   - 增加支持 `turns` 参数（如 `turns=5`）；
   - 在按轮切片模式下，以完整的对话轮次（即用户消息及其接续的全部 assistant steps）为原子单位，保证每一轮的提问、折叠过程与最终回答完整返回，不再跨页断裂；
   - 保持现有 `limit`、`before` 及无参模式 100% 向后兼容。

2. **客户端统一按轮次加载与翻页**：
   - 首次加载会话历史时拉取最新 5 个完整轮次；
   - 顶部加载更多按钮文案更新为 `加载更早历史（已呈现 X／Y 轮）`，与用户的视觉折叠轮次心智 100% 对齐；
   - 移除不稳定的“跨页补齐”妥协逻辑，渲染直接保证每轮结构天然闭环。

## Alternatives considered

1. **完全取消分页，仅靠折叠**：
   - Q20 仅 2GB RAM，WebKit 537.35 内核在解析成百上千条消息的超长 JSON 时极易触发 OOM，且 DOM 节点过多会拖慢滚动渲染。不可取。
2. **维持按消息切片，继续用前端自动多次补齐**：
   - 复杂脆弱，当轮次中间消息超过补齐上限时依然断裂，治标不治本。

## Consequences

- 彻底消除“懒加载与轮次折叠打架”的问题，对话历史在任何时候都按完整轮次呈现。
- 大幅简化客户端渲染与补齐状态机，降低老旧 CPU 的额外异步请求开销。
- 100% 通过 ES5 门禁与端到端自动化测试。
